# Безопасность Coralink

## 1. Модель угроз

| Противник | Возможности | Что защищает Coralink |
|---|---|---|
| Сервер (honest-but-curious) | видит все запросы, хранит очередь | E2EE сообщений и зашифрованные снимки питомцев; ключи хранятся на устройстве |
| Сетевой перехватчик | читает/меняет трафик | TLS (в продакшене), подпись сообщений Signal, MAC |
| Кража устройства | доступ к файлам | SQLCipher + Keystore/Keychain |
| Другой пользователь | подбор кода, спам | rate limit, HMAC-хеши кодов, лимит попыток |
| Инсайдер сервера | доступ к БД | нет открытого текста, нет приватных ключей |
| Подмена ключа | MITM при обмене | подписанные prekey, доверие identity, предупреждение `identity_changed` |

**Вне модели:** скомпрометированное устройство (malware/root), принуждение к разблокировке, глобальный анализ трафика (metadata), квантовые атаки.

## 2. Криптография

- **E2EE**: Signal Protocol — X3DH, Double Ratchet, Curve25519, AES-256-CBC + HMAC-SHA256 (внутри libsignal), XEdDSA для подписи prekey.
- **Identity + sessions + prekeys**: хранятся в Keychain/Keystore, не в БД сообщений.
- **Локальная БД**: SQLCipher с 256-битным ключом из CSPRNG (Android/iOS).
- **Токен сессии**: JWT HS256, 30 дней, хранится в secure storage.
- **Коды входа**: 6 цифр, HMAC-SHA256 с серверным pepper, TTL 5 минут, не более 5 попыток, сравнение через `timingSafeEqual`.
- **Транспорт**: HTTPS/WSS в продакшене; dev-режим допускает локальный HTTP только для `127.0.0.1`, `localhost`, `10.0.2.2` (Android network security config).
- **Режим входа**: регистрация и вход по никнейму и паролю (`/auth/register`,
  `/auth/login`). Пароль проверяется через scrypt (N=16384, r=8, p=1) с серверным
  pepper; на сервере хранится только хеш пароля. SMS/e-mail-коды
  (`/auth/request-code`, `/auth/verify`) сохранены как опциональный путь. Периметр
  безопасности в приватном развёртывании — сеть доступа (например, tailnet
  Tailscale); кто первым занял никнейм — владеет им, пароль добавляет второй фактор.
- **Мультидевайс (бэкап ключей)**: полное состояние Signal (identity, prekeys,
  sessions) и ключи групп шифруются AES-GCM ключом, выведенным из пароля через
  PBKDF2-HMAC-SHA256 (200 000 итераций), и хранятся на сервере как непрозрачный
  блоб с солью. Сервер не может его расшифровать; новое устройство восстанавливает
  идентичность при входе с тем же паролем. Неверный пароль → аутентификация тега
  GCM не проходит, ключи не раскрываются.

## 3. Что видит сервер

Хранит:

- никнейм, имя, хеш пароля (scrypt);
- публичные ключи (identity, signed prekey, one-time prekeys);
- контакты;
- **шифротекст** сообщений (1-на-1 и групповых) до подтверждения доставки (TTL 30 дней);
- время создания/доставки/прочтения;
- состав групп (участники, роли, заголовок/аватар) — метаданные групп;
- **зашифрованный бэкап ключей** (AES-GCM блоб + соль) — сервер не читает содержимое;
- метаданные питомцев, участников, тип действия, порядок операций и зашифрованные снимки;
- push-токены (если зарегистрированы);
- настройку видимости присутствия (`everyone / contacts / nobody`).

Не хранит:

- открытый текст и медиа;
- приватные ключи (только их шифротекст в бэкапе);
- ключи групп и питомцев в открытом виде;
- имя, вид и статистику питомца;
- историю чатов после доставки;
- пароли в открытом виде (только хеш).

Метаданные (кто, кому, когда) остаются видимыми — это свойство любого relay-мессенджера и явно описано в политике конфиденциальности.

## 4. Perfect Forward Secrecy

Double Ratchet генерирует новые ключи на каждое сообщение. Компрометация текущих ключей не раскрывает прошлые сообщения. Смена ключей также ограничивает последствия компрометации в будущем (post-compromise security).

## 5. Проверка личности

В протоколе уже вычисляется fingerprint identity key (`SignalService.identityFingerprint`). При смене ключа собеседника отправка блокируется с ошибкой `identity_changed`.

В текущем UI нет экрана сравнения safety number — это запланировано в дорожной карте. До его появления пользователям рекомендуется сверять личность по независимому каналу.

## 6. Защита сервера

- JWT-секрет и pepper обязательны в production (минимум 32 символа), иначе сервер не стартует.
- Параметризованные SQL-запросы, лимит JSON-тела 1 МБ, WS payload до 16 МБ.
- CORS-allowlist, security-заголовки, `Cache-Control: no-store` для API.
- Rate limit: 5 кодов/час на IP, 60 с на номер, 10 проверок/15 мин, 300 запросов/мин.
- Коды и токены не логируются (redaction).
- Сообщения удаляются по TTL; аккаунт можно удалить (`DELETE /api/v1/me`), что каскадно чистит ключи, контакты, очередь и push-токены.
- Видимость присутствия применяется сервером: при `nobody` статус не рассылается и HTTP `/presence` возвращает offline; при `contacts` — только взаимным контактам.
- Рекомендуется reverse proxy с TLS, HSTS, лимитами и fail2ban.

## 7. Ограничения текущей версии

1. **Нет внешнего аудита.** Используется проверенная библиотека Signal Protocol, но интеграция и UI не аудированы.
2. **Мультидевайс — «клон с общей идентичностью».** Вход на новом устройстве
   восстанавливает ключи из зашифрованного бэкапа, поэтому история и группы
   расшифровываются. Полноценного concurrent multi-device (отдельные identity/session
   на каждое устройство + per-recipient sender keys Signal) нет: если оба устройства
   одновременно активно пишут одному собеседнику, Double Ratchet может разойтись.
3. **Групповое E2EE** реализовано через симметричные AES-GCM ключи группы,
   распределяемые по 1-на-1 Signal-каналу. Это даёт E2EE, но без per-member
   sender-key-рэтчета Signal: ротация ключа группы и post-compromise security в
   группах проще, чем в 1-на-1.
4. **Desktop-БД не зашифрована.** Windows-сборка — preview; для продакшена нужен SQLCipher-порт или шифрование на уровне полей.
5. **Web-история только в памяти.** Это снижает риск утечки, но исключает офлайн-историю.
6. **SMS-провайдер не подключён.** Dev-код возвращается клиенту; в продакшене нужен реальный SMS-шлюз и отключение `DEV_MODE`.
7. **Push-уведомления**: сервер хранит токены, но отправка FCM/APNS не реализована. Локальные уведомления работают только пока процесс приложения активен.
8. **TURN не развёрнут.** Без TURN часть NAT-сценариев уйдёт на relay — это безопасно, но медленнее.
9. **Нет проверки safety number в UI** (см. выше).

## 8. Рекомендации для продакшена

- TLS 1.2+, HSTS, современные шифры; WSS.
- Секреты в менеджере секретов, ротация JWT-секрета.
- Отдельный TURN с короткоживущими credentials.
- SMS-провайдер с защитой от фрода (лимиты по номеру/стране).
- FCM/APNS с минимальным payload (без текста сообщения).
- Резервное копирование БД с шифрованием; мониторинг 429/401.
- Пентест и аудит криптографической интеграции.

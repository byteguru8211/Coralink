# Архитектура Coralink

## 1. Общая картина

Coralink состоит из двух самостоятельных приложений:

- **Клиент** — Flutter (Android / Windows / Web; iOS-каркас готов к сборке на macOS).
- **Сервер** — Node.js 24, HTTP API + WebSocket, встроенный `node:sqlite`.

Сервер выполняет роль **signaling + relay**: он помогает устройствам найти друг
друга, хранит публичные ключи, передаёт непрозрачный шифротекст и ретранслирует
signaling звонков. Открытый текст сообщений не покидает устройство.

```
Flutter-клиент A ──WebSocket/HTTPS (relay сообщений)──► Node.js ──► Flutter-клиент B
        │                                                        ▲
        └────WebRTC (медиа звонка напрямую, поверх tailnet)──────┘
                     signaling (offer/answer/ICE) идёт через сервер

┌──────────────────────────────────────────────────────────────────┐
│ Node.js: auth · keys · groups · relay · call-signaling · presence │
│ SQLite: users, prekeys, contacts, queue, groups, key_backup, push │
└──────────────────────────────────────────────────────────────────┘
```

> Примечание: прямая доставка через **WebRTC DataChannel отключена**. Bundled
> libwebrtc форсирует Unified Plan и обрывает процесс на `createDataChannel`
> (`Check failed: !IsUnifiedPlan()`), поэтому вся доставка сообщений идёт через
> WebSocket-relay. WebRTC используется только для медиа звонков (аудио/видео).

## 2. Слои клиента

```
presentation/   экраны, виджеты, Riverpod-контроллеры
      │
domain/         сущности (User, Chat, Message, Group), правила
      │
services/       MessageService, EchoSearch, Audio, Notifications, Export,
                VoiceRecorder, KeepAlive
      │
network/        RealtimeService (WS-relay), CallService (WebRTC), P2PManager (отключён)
security/       SignalService, PersistentSignalStore, GroupCrypto, KeyBackup
      │
data/           ApiClient, LocalStore (SQLCipher/SQLite/memory), SecureStore
```

Принципы:

- **Однонаправленный поток**: UI читает состояние из Riverpod, действия вызывают методы контроллера, контроллер обращается к сервисам.
- **Порты и адаптеры**: `LocalStore` — интерфейс; реализации для mobile (SQLCipher), desktop (FFI) и web (memory). `SecureStore` — единая обёртка над Keychain/Keystore/WebCrypto.
- **Изоляция криптографии**: `SignalService` не знает о UI и БД сообщений; состояние ratchet хранится отдельно в защищённом хранилище.
- **Платформенные различия** спрятаны за условными импортами (`local_store_opener.dart`, `chat_exporter.dart`).

### 2.1. Сессия

`SessionController` — единственный владелец состояния входа:

```
booting → unauthenticated → onboarding → authenticated
                 ↘ error (сеть) ↗
```

После успешного входа создаётся `ClientBundle` — набор сервисов, привязанных к пользователю и токену. При выходе bundle освобождается, но Signal-идентичность остаётся в secure storage, чтобы при повторном входе сохранить safety number и сессии.

Токен хранится в Keychain/Keystore. При старте клиент:
1. читает токен и `sub` из JWT;
2. пробует `GET /me`;
3. при сетевой ошибке использует кэшированного пользователя и работает офлайн;
4. при 401 — очищает токен и показывает вход.

## 3. Сквозное шифрование

Используется **Signal Protocol** (`libsignal_protocol_dart`):

- Identity Key (Curve25519), registrationId.
- Signed PreKey с подписью XEdDSA.
- 100 one-time prekeys.
- X3DH при первом сообщении, далее Double Ratchet (PFS + post-compromise security).
- Каждый peer-адрес — `(userId, deviceId=1)`.

`PersistentSignalStore` реализует интерфейсы Signal и сериализует состояние в JSON, который целиком лежит в Keychain/Keystore. После каждой мутации состояние перезаписывается.

Формат транспорта:

```
base64( [typeByte][libsignal ciphertext] )
```

`typeByte` позволяет отличить `PreKeySignalMessage` (3) от `SignalMessage` (2), не раскрывая тип серверу.

Открытый текст — JSON-envelope:

```json
{"v":1,"type":"text","text":"Привет","sentAt":1730000000000}
{"v":1,"type":"image","image":"<base64>","meta":{"mime":"image/jpeg","name":"photo.jpg"}}
{"v":1,"type":"file","data":"<base64>","meta":{"mime":"application/pdf","name":"doc.pdf","size":12345}}
{"v":1,"type":"audio","data":"<base64>","meta":{"mime":"audio/mp4a-latm","size":...,"durationMs":...}}
{"v":1,"type":"video","data":"<base64>","meta":{"mime":"video/mp4","name":"clip.mp4","size":...}}
{"v":1,"type":"video_note","data":"<base64>","meta":{"mime":"video/mp4","size":...,"durationMs":...}}
{"v":1,"type":"reaction","targetId":"<uuid>","reaction":"🌿"}
{"v":1,"type":"delete","targetId":"<uuid>"}
{"v":1,"type":"groupKey","groupId":"<uuid>","key":"<base64 AES-GCM key>"}
{"v":1,"type":"groupMeta","title":"...","avatar":"...","memberCount":N}
```

Байты вложений лежат **внутри шифротекста** (в `data`/`image` envelope), а не в
служебном `meta` поверх канала: серверный relay ограничивает `meta` 16 КБ, и
большой base64 в `meta` приводил к отклонению доставки получателю.

Сервер видит только base64-шифротекст и технический `kind` (`text` / `image` /
`file` / `audio` / `video` / `video_note` / `control`).

### 3.1. Групповое E2EE

Каждая группа имеет симметричный 256-битный AES-GCM ключ (`GroupCrypto`). Ключ
генерирует создатель и рассылает участникам зашифрованным сообщением `groupKey`
по их 1-на-1 Signal-каналам; ключ хранится в secure storage под `group.key.<id>`.
Групповые сообщения шифруются этим ключом и ретранслируются сервером всем
участникам. Смена названия/аватара рассылается как `groupMeta`, чтобы у всех
обновлялось в реальном времени.

### 3.2. Бэкап ключей (мультидевайс)

`KeyBackup` сериализует состояние Signal (identity, prekeys, sessions), ключи групп
и личных/парных питомцев, шифрует AES-GCM-ключом из PBKDF2-HMAC-SHA256 (пароль +
соль, 200k итераций) и загружает на сервер как непрозрачный блоб. Локальная ревизия
ratchet не позволяет старому бэкапу откатить новое состояние. Опубликация prekey
отслеживается по id: использованный ключ не публикуется повторно. При входе на новом
устройстве бэкап восстанавливает identity; при отсутствии ключей и бэкапа вход
завершается ошибкой, а не молчаливой выдачей новой identity.

### 3.3. Тамагочи

Личный питомец имеет scope `personal`, парный — `direct` с взаимным приглашением,
групповой — `group`. Сервер хранит участников, статус, монотонный `seq` и зашифрованный
снимок; операции содержат зашифрованное действие и назначаемый сервером порядок.
Личный/парный ключ питомца лежит в защищённом хранилище и бэкапе, групповой использует
ключ группы. Клиент применяет операции последовательно, поэтому concurrent care не
теряется. Offline-действия хранятся в отдельной локальной очереди. Сервер проверяет
участие и лимиты, но не видит имя, вид или статистику.

## 4. Доставка сообщений

Порядок отправки (через relay; прямые DataChannel отключены):

1. Сообщение шифруется и сохраняется локально со статусом `sending`.
2. Отправляется через WebSocket на сервер (`message` для 1-на-1, `group.send` для
   групп). Сервер кладёт его в очередь получателя и доставляет, если тот онлайн.
3. Получатель:
   - дедуплицирует по `id`;
   - расшифровывает (Signal или AES-GCM для групп);
   - сохраняет;
   - подтверждает (`message.ack` / ack групповых) и отправляет read-receipt, если чат открыт.
4. Сервер помечает сообщение доставленным и уведомляет отправителя.
5. Сообщение всегда кладётся в локальный `outbox` и удаляется только после
   серверного `message.ack`. После reconnect очередь синхронизируется, а HTTP
   `/messages/status` восстанавливает доставку/чтение, даже если WS-событие было пропущено.

Неудачная расшифровка (например, пришло раньше, чем создан session) не теряет
сообщение: сохраняется шифротекст и повторная попытка после установления сессии.

### 4.1. Звонки (WebRTC) и история звонков

- `CallService` поднимает `RTCPeerConnection` для аудио/видео звонка; signaling
  (offer/answer/ICE) идёт через сервер событием `call`.
- Медиа идёт напрямую между устройствами поверх tailnet (host-кандидаты), TURN не
  обязателен; STUN опционален.
- ICE-кандидаты буферизуются до установки remote description (иначе кандидаты,
  пришедшие пока вызываемый «звонит», терялись бы и рукопожатие не завершалось).
- Разрешения на микрофон/камеру запрашиваются перед `getUserMedia`; ошибки
  signaling не должны ронять isolate (обёрнуты в try/catch).
- Сброс определяется и по явному `call/hangup`, и по состоянию соединения
  (`disconnected`), чтобы висящий звонок завершался.
- `CallService` по завершении отдаёт `CallSummary`; `ClientBundle` сохраняет его
  в локальную таблицу `calls` (направление, видео/аудио, ответили ли, длительность).
  Лента чата показывает звонки как системные плашки в общей хронологии, поэтому
  история разговора не теряется.
- Экран звонка: видео на весь экран с PiP-самопрессом, таймер, микрофон, динамик,
  камера, переключение камеры, состояние соединения и завершение.

### 4.2. Присутствие

- Сервер знает, есть ли живой сокет (`online`).
- Клиент сообщает `active` / `away` по жизненному циклу приложения и после 5 минут бездействия.
- Присутствие рассылается контактам; HTTP `GET /presence` доступен для точечного опроса.
- UI: 4 состояния, пульсирующий ореол, шелест листьев при онлайне.

## 5. Локальное хранилище

### Мобильные платформы
SQLCipher, ключ 256 бит генерируется CSPRNG и хранится в Keychain/Keystore.

### Desktop
`sqflite_common_ffi`, обычный SQLite. Windows — полноценный клиент: постоянное
окно (`window_manager`), иконка в трее и закрытие окна в трей (`tray_manager`),
полная история, звонки и уведомления. Ограничение одно: файл desktop-БД не шифруется
SQLCipher, в отличие от мобильных платформ.

### Web
История в памяти вкладки. Это demo/preview; постоянное хранение на web не реализовано, чтобы не создавать иллюзию защищённого хранилища.

Схема:

```sql
users(id, phone, username, password_hash, name, about, avatar, avatar_color, last_seen, presence, presence_visibility)
chats(id, peer_id, peer_name, peer_avatar, peer_avatar_color, is_group, member_count,
      last_message_text, last_message_at, unread_count, archived, pinned, muted, updated_at)
messages(id, chat_id, sender_id, text, kind, status, created_at,
         delivered_at, read_at, meta, image_b64, reactions, archived, deleted)
contacts(id, phone, name, about, avatar_color, last_seen, presence, added_at)
outbox(id, chat_id, payload, created_at, attempts)
calls(id, peer_id, started_at, video, outgoing, answered, duration_seconds)
```

На сервере (`node:sqlite`) дополнительно: `prekeys`, `auth_codes`, `groups`,
`group_members`, `group_messages`, `group_message_receipts`, `push_tokens`, `key_backup`, `pets`, `pet_members`,
`pet_operations`.

Открытый текст в БД — нормальное решение: история должна быть доступна офлайн. На мобильных она защищена шифрованием всей БД.

## 6. «Приливы и отливы»

- При входе чаты без активности 7+ дней помечаются архивными (кроме закреплённых).
- Сообщения старше 7 дней получают флаг `archived` и скрываются из ленты; в чате появляется плашка «Показать архив (N)».
- Новое сообщение автоматически возвращает чат из архива.
- Ручной архив доступен свайпом и в контекстном меню.

## 7. Эхолокация

Локальный поиск без отправки данных:

1. Нормализация (регистр, `ё → е`, удаление пунктуации).
2. Токенизация + список стоп-слов (RU/EN).
3. Лёгкий стемминг русских окончаний.
4. Граф синонимов (встреча ↔ созвон, фото ↔ снимок и т.д.).
5. Совпадение токенов, синонимов, триграммное сходство (опечатки), бонус за подстроку.
6. Ранжирование и подсветка в UI.

Поиск выполняется по локальной БД, сообщения не покидают устройство.

## 8. Уведомления и звуки

- Три режима: со звуком, без звука и выключены. Старые значения `advanced/minimal/medium`
  мигрируют в ближайший рабочий режим.
- Android создаёт отдельные стандартный, silent и call каналы. Звук выбирает система,
  поэтому нет двойного воспроизведения app cue и channel sound.
- Пока приложение на экране, показывается встроенный баннер; в фоне — системное
  уведомление, одно на чат. Входящий звонок использует отдельный call канал.
- Notification permission запрашивается после первого кадра; cold-start tap
  сохраняется и открывается после авторизации.
- Push после убийства процесса не гарантирован: FCM/APNS sender не подключён.
  Foreground-service переключатель и пакет удалены как не создающие реальной гарантии.
- Windows: уведомления через `flutter_local_notifications` с AppUserModelId.
- Звуки природы выбираются отдельно для присутствия, отправки, получения и звонка.

## 9. Ошибки и устойчивость

- Сетевые ошибки → `ApiException(status 0)`; UI показывает мягкие сообщения.
- WS-клиент переподключается с экспоненциальной задержкой до 30 с.
- Outbox повторяет отправку каждые 8 с и при восстановлении соединения.
- Неудачная расшифровка не теряет сообщение: сохраняется заглушка «Не удалось расшифровать».
- Смена identity key собеседника → `identity_changed`, сообщение не отправляется, пользователь предупреждается.
- Все исключения логируются без токенов, кодов и открытого текста.

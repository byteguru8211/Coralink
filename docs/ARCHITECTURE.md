# Архитектура Coralink

## 1. Общая картина

Coralink состоит из двух самостоятельных приложений:

- **Клиент** — Flutter (Android / Windows / Web; iOS-каркас готов к сборке на macOS).
- **Сервер** — Node.js 24, HTTP API + WebSocket, встроенный `node:sqlite`.

Сервер выполняет роль **signaling + relay**: он помогает устройствам найти друг друга, хранит публичные ключи и передаёт непрозрачный шифротекст. Открытый текст сообщений не покидает устройство.

```
Flutter-клиент A ──WebRTC DataChannel──► Flutter-клиент B
        │                                  ▲
        │ WebSocket + HTTPS                │
        ▼                                  │
┌─────────────────────────────────────────────────────┐
│ Node.js: auth · keys · signaling · relay · presence  │
│ SQLite: users, prekeys, contacts, queue, push tokens │
└─────────────────────────────────────────────────────┘
```

## 2. Слои клиента

```
presentation/   экраны, виджеты, Riverpod-контроллеры
      │
domain/         сущности (User, Chat, Message), правила
      │
services/       MessageService, EchoSearch, Audio, Notifications, Export
      │
network/        RealtimeService (WS), P2PManager (WebRTC)
security/       SignalService, PersistentSignalStore
      │
data/           ApiClient, LocalStore (SQLCipher/SQLite/memory), SecureStore
```

Принципы:

- **Однонаправленный поток**: UI читает состояние из Riverpod, действия вызывают методы контроллера, контроллер обращается к сервисам.
- **Порты и адаптеры**: `LocalStore` — интерфейс; реализации для mobile (SQLCipher), desktop (FFI) и web (memory). `SecureStore` — единая обёртка над Keychain/Keystore/WebCrypto.
- **Изоляция криптографии**: `SignalService` не знает о UI и БД сообщений; состояние ratchet хранится отдельно в защищённом хранилище.
- **Платформенные различия** спрятаны за условными импортами (`local_store_opener.dart`, `chat_exporter.dart`).

### 2.1. Сессия

`SessionController` — единственный владелец состояния входа:

```
booting → unauthenticated → onboarding → authenticated
                 ↘ error (сеть) ↗
```

После успешного входа создаётся `ClientBundle` — набор сервисов, привязанных к пользователю и токену. При выходе bundle освобождается, но Signal-идентичность остаётся в secure storage, чтобы при повторном входе сохранить safety number и сессии.

Токен хранится в Keychain/Keystore. При старте клиент:
1. читает токен и `sub` из JWT;
2. пробует `GET /me`;
3. при сетевой ошибке использует кэшированного пользователя и работает офлайн;
4. при 401 — очищает токен и показывает вход.

## 3. Сквозное шифрование

Используется **Signal Protocol** (`libsignal_protocol_dart`):

- Identity Key (Curve25519), registrationId.
- Signed PreKey с подписью XEdDSA.
- 100 one-time prekeys.
- X3DH при первом сообщении, далее Double Ratchet (PFS + post-compromise security).
- Каждый peer-адрес — `(userId, deviceId=1)`.

`PersistentSignalStore` реализует интерфейсы Signal и сериализует состояние в JSON, который целиком лежит в Keychain/Keystore. После каждой мутации состояние перезаписывается.

Формат транспорта:

```
base64( [typeByte][libsignal ciphertext] )
```

`typeByte` позволяет отличить `PreKeySignalMessage` (3) от `SignalMessage` (2), не раскрывая тип серверу.

Открытый текст — JSON-envelope:

```json
{"v":1,"type":"text","text":"Привет","sentAt":1730000000000}
{"v":1,"type":"image","image":"<base64>","meta":{"mime":"image/jpeg","name":"photo.jpg"}}
{"v":1,"type":"reaction","targetId":"<uuid>","reaction":"🌿"}
{"v":1,"type":"delete","targetId":"<uuid>"}
```

Сервер видит только base64-шифротекст и технический `kind` (`text` / `image` / `control`).

## 4. Доставка сообщений

Порядок отправки:

1. Сообщение шифруется, сохраняется локально со статусом `sending`.
2. Отправляется через WebSocket на сервер (сервер ставит в очередь получателя).
3. Параллельно, если есть открытый DataChannel, копия уходит напрямую peer-у.
4. Получатель:
   - дедуплицирует по `id`;
   - расшифровывает;
   - сохраняет;
   - отправляет ack на сервер (`message.ack`) и read-receipt, если чат открыт;
   - отвечает ack по DataChannel, если сообщение пришло по P2P.
5. Сервер помечает сообщение доставленным и уведомляет отправителя.
6. Если сокет недоступен, сообщение кладётся в локальный `outbox` и повторяется после реконнекта. Сервер дедуплицирует по `id`.

Такой гибрид даёт скорость P2P и надёжность серверной очереди: P2P-копия может прийти раньше, relay-копия гарантирует доставку и корректные статусы.

### 4.1. WebRTC

- Инициатор соединения — пользователь с лексикографически меньшим `userId` (детерминированно, без гонок).
- Один `RTCPeerConnection` и один DataChannel `coralink-data` на чат.
- SDP и ICE передаются через сервер (`signal`-события), сами данные — напрямую.
- STUN по умолчанию `stun:stun.l.google.com:19302`; TURN задаётся через `--dart-define`.
- При разрыве/смене сети соединение пересоздаётся; сообщения продолжают идти через relay.

### 4.2. Присутствие

- Сервер знает, есть ли живой сокет (`online`).
- Клиент сообщает `active` / `away` по жизненному циклу приложения и после 5 минут бездействия.
- Присутствие рассылается контактам; HTTP `GET /presence` доступен для точечного опроса.
- UI: 4 состояния, пульсирующий ореол, шелест листьев при онлайне.

## 5. Локальное хранилище

### Мобильные платформы
SQLCipher, ключ 256 бит генерируется CSPRNG и хранится в Keychain/Keystore.

### Desktop
`sqflite_common_ffi`, обычный SQLite (preview-платформа). Это осознанное ограничение: desktop-сборка предназначена для разработки и демонстрации.

### Web
История в памяти вкладки. Это demo/preview; постоянное хранение на web не реализовано, чтобы не создавать иллюзию защищённого хранилища.

Схема:

```sql
users(id, phone, name, about, avatar_color, last_seen, presence)
chats(id, peer_id, peer_name, ..., last_message_text, last_message_at,
      unread_count, archived, pinned, muted, updated_at)
messages(id, chat_id, sender_id, text, kind, status, created_at,
         delivered_at, read_at, meta, image_b64, reactions, archived, deleted)
contacts(id, phone, name, about, avatar_color, last_seen, presence, added_at)
outbox(id, chat_id, payload, created_at, attempts)
```

Открытый текст в БД — нормальное решение: история должна быть доступна офлайн. На мобильных она защищена шифрованием всей БД.

## 6. «Приливы и отливы»

- При входе чаты без активности 7+ дней помечаются архивными (кроме закреплённых).
- Сообщения старше 7 дней получают флаг `archived` и скрываются из ленты; в чате появляется плашка «Показать архив (N)».
- Новое сообщение автоматически возвращает чат из архива.
- Ручной архив доступен свайпом и в контекстном меню.

## 7. Эхолокация

Локальный поиск без отправки данных:

1. Нормализация (регистр, `ё → е`, удаление пунктуации).
2. Токенизация + список стоп-слов (RU/EN).
3. Лёгкий стемминг русских окончаний.
4. Граф синонимов (встреча ↔ созвон, фото ↔ снимок и т.д.).
5. Совпадение токенов, синонимов, триграммное сходство (опечатки), бонус за подстроку.
6. Ранжирование и подсветка в UI.

Поиск выполняется по локальной БД, сообщения не покидают устройство.

## 8. Уведомления и звуки

- 4 режима: минимальный (вибрация), средний (мягкий звук + свет), расширенный (heads-up), офлайн (только внутри приложения).
- Android-каналы создаются с разными importance/light/sound.
- iOS-разрешения запрашиваются по действию пользователя.
- Windows/Web: сервис уведомлений отключён, интерфейс продолжает работать.
- Звуки (шелест, капля, всплеск, вдох, всплеск-сигнал) синтезированы и лежат в `assets/sounds`.

## 9. Ошибки и устойчивость

- Сетевые ошибки → `ApiException(status 0)`; UI показывает мягкие сообщения.
- WS-клиент переподключается с экспоненциальной задержкой до 30 с.
- Outbox повторяет отправку каждые 8 с и при восстановлении соединения.
- Неудачная расшифровка не теряет сообщение: сохраняется заглушка «Не удалось расшифровать».
- Смена identity key собеседника → `identity_changed`, сообщение не отправляется, пользователь предупреждается.
- Все исключения логируются без токенов, кодов и открытого текста.
